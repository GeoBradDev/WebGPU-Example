Risk tier: Medium. Dependency-only change with no app logic edits expected, but a maplibre-gl major upgrade (5 to 6) alters map rendering behavior that unit tests cannot exercise, and the lockfile change is large.

Domain skills:

## Acceptance criteria

1. `npm audit --omit=dev` reports no critical or high findings.
2. No pre-release versions remain in `package.json`, and the `overrides` block is gone.
3. `npm ls` shows no unused direct dependencies: `axios`, `deck.gl`, `@deck.gl/react`, `@loaders.gl/core`, `@loaders.gl/json` and `@luma.gl/webgpu` are removed from `package.json` (`@luma.gl/webgpu` because issue #8 decided RENDER will report deck.gl's actual device rather than wire WebGPU rendering).
4. `maplibre-gl` is on a 6.x release above 6.4.0 (outside GHSA-jrc7-96c5-q579), `react-map-gl` on a version compatible with it, `@deck.gl/layers` and `@deck.gl/mapbox` on 9.4.x, `vite` on stable `^8.3`, `@vitejs/plugin-react` on a release whose peer range accepts Vite 8 stable, `vitest` and `@vitest/ui` on a patched release (latest 4.x, so no new major).
5. `npm ci`, `npm test` and `npm run build` pass; `npm run lint` shows no new errors (the 2 pre-existing `react-hooks/purity` errors in `src/hooks/useStressPoints.js` belong to issue #12).
6. Live smoke test: the built app (`vite preview`) renders the CARTO basemap, the airports and ports deck.gl layers, and the console shows no new errors.

## Files that change

- `package.json`: version ranges, removals, `overrides` removed.
- `package-lock.json`: regenerated by npm.
- `vite.config.js`: drop `deck.gl`, `@deck.gl/react` and `@luma.gl/webgpu` from `optimizeDeps.exclude` (packages no longer installed as direct deps); leave the other entries.
- `src/manifest.test.js` (new): guard test reading `package.json`.
- Any `src/` file only if the maplibre 6 / react-map-gl upgrade forces an API change (record it here if so).
- `src/config/maplibreWorker.js` (new) and `src/components/MapView.jsx` (one import): forced by maplibre 6. It locates its web worker from `import.meta.url`, which Vite does not follow, so the first live drive showed `Error: Worker failed to load` twice and a blank basemap (no vector tiles requested). Per the maplibre 6 docs (Installation > Vite, and the v5-to-v6 migration guide "setWorkerUrl() is bundler-only"), the module calls `setWorkerUrl()` with `maplibre-gl/dist/maplibre-gl-worker.mjs?worker&url`, and MapView imports it before any map is created.
- `src/config/maplibreWorker.test.js` (new): build-level regression test (node environment, `vite build` with `write: false`) asserting the bundle emits a `maplibre-gl-worker` file and app code references it. Red before the fix.

- Vite 8 stable vs beta config differences; `vite build` proves it.
- Not doing: vitest 5 major (issue asks for a patched release, 4.x suffices if audit is clean), Dependabot/CI audit step (issue #12), lint fixes (issue #12), wiring WebGPU rendering (issue #8).
